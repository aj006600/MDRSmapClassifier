# Usage

怎麼使用已經啟動的服務。安裝與啟動見 [README](../README.md#quick-start),用詞的定義見 [GLOSSARY.md](../GLOSSARY.md)。

## Run

在網頁 http://localhost:3000:

1. 輸入股票代號(上市、上櫃皆可),選擇 Horizon(5、10 或 20 個交易日,預設 10),按「執行」。
2. 「工作」區塊列出每個工作的狀態:排隊中、執行中、完成或失敗。執行中會標出目前的階段:抓資料、Search、逐日預測。
3. 工作完成後,結果顯示在下方。成功執行過的股票列在最下面的「執行過的股票」,點選就能再看它的結果。

同一支股票同一個 Horizon,每次執行做的事不同:

| 情況 | 服務做的事 | 大約的時間 |
|------|------------|------------|
| 第一次執行 | 抓約四年的資料、做 Search、從起點逐日預測到最新的交易日 | 幾分鐘 |
| 之後再執行 | 只抓上次之後的日子,沿用參數補算新增的交易日 | 幾秒 |
| 同一天再執行 | 直接回傳當天已存的結果,不重算也不抓資料 | 立即 |
| 要求重新搜尋 | 以最新的交易日重設起點,重新做 Search | 幾分鐘 |

其他行為:

- 可以連續發起好幾支股票。同一時間只跑一個,其餘依發起的順序排隊。
- 同一支股票同一個 Horizon 已經在排隊或執行時,再發起一次不會多開一個工作。
- 關掉網頁再回來,排隊中與執行中的工作仍然看得到。
- 服務重新啟動時,當下執行中的工作會標為失敗,要重新發起;排隊中的工作照原本的順序繼續。

工作失敗時,畫面會顯示失敗原因:

| 失敗原因 | 怎麼處理 |
|----------|----------|
| 查無股票代號 | 確認代號是否正確 |
| 歷史資料不足 | 起點之前需要 600 個交易日(約兩年半)的資料當 Library,上市時間太短的股票無法執行 |
| 資料來源的請求額度用盡 | 稍後再試,或在 `.env` 填入 FinMind token(見 [README](../README.md#finmind-token)) |
| 資料來源連不上或回應異常 | 確認網路連線,稍後再試 |
| 資料來源的資料有缺漏 | FinMind 的資料有服務補不了的缺漏,這支股票目前無法執行;失敗原因會列出缺的日子 |
| 程式錯誤 | 請到 GitHub 開 issue 回報,附上失敗原因 |

## Reading Results

結果的開頭有兩個日期:

- **資料用到的交易日**:這次執行用到的最後一個交易日。當天的資料還沒公布完時,是前一個資料齊全的交易日。
- **Search 的日期與起點**:參數是哪一天做 Search 找到的。起點是當時最新的交易日往前 100 個交易日;Search 只用起點(含)以前的資料,逐日預測從起點開始。

### Forecast

最近 Horizon 個交易日的實際 Direction 都還沒揭曉,所以每一天各有一筆 Forecast,並標明它依據的交易日。日期為某一天的 Forecast,回答的是:從隔天起的 Horizon 個交易日,平均收盤價會不會不低於那一天的收盤價。

日期等於「資料用到的交易日」的那一筆看得最遠,是模型對接下來 Horizon 個交易日的判斷。日期較早的幾筆,它們看的期間已經過了一部分。每一筆 Forecast 在 Horizon 個交易日之後揭曉,下一次執行會把它轉入 Backtest。

### Backtest

- **準確率**:計分的日子裡,預測的 Direction 與實際相同的比例。
- **計分天數**:已經揭曉實際 Direction 的天數。第一次執行之後約是 100 減 Horizon 天,之後每多一個交易日就多一天。
- **Direction 為 1 的天數比例**:同一段計分的日子裡,實際 Direction 為 1 的比例。它等於每天都猜 1 的準確率,所以準確率要高於這個比例,模型才比每天都猜 1 好。股價長期上漲時這個比例會遠高於一半,只看準確率容易高估模型。
- **逐日明細**:每一天的預測、實際與對錯,用來看模型錯在哪些日子。

讀 Backtest 時要注意:

- Backtest 的每一天都在起點之後,Search 沒看過這些日子的資料,所以準確率不是因為事先看過答案而虛高。
- 計分天數少時,準確率的起伏很大。幾十天的準確率差幾個百分點,不足以說明模型變好或變差。
- 同樣的資料與設定,每次算出相同的結果。

## When to Re-search

沿用參數時,Backtest 一直累積:從起點以來的每一天都用同一組參數預測,也都沒被 Search 看過,天數越多越有參考價值。代價是參數只反映做 Search 當時的市況。

可以考慮重新搜尋的情況:

- 參數已經用了很久(結果頁顯示 Search 的日期),這段期間市況變了很多。
- 逐日明細裡最近一段時間錯得特別多,或準確率長期低於 Direction 為 1 的天數比例。
- 升級到改了特徵或演算法的版本之後。已存的參數是舊版本找到的,繼續沿用就不會用到新的做法。

重新搜尋會以最新的交易日重設起點、重新做 Search,需要幾分鐘。原本的逐日預測整個換掉:Backtest 從新的起點重新計算,不會混到用舊參數算的日子,但累積的天數也從頭算起。

在網頁上按結果頁的「重新搜尋」;經由 API 則是發起執行時帶 `"re_search": true`。

## Data Publication Time

台股收盤後,FinMind 分批更新當天的資料。依 FinMind 的文件,三大法人的買賣超約 20:00 更新,融資餘額與外資持股約 21:00 更新(台灣時間,這個時間沒有實測)。服務要等一個交易日的價格與籌碼都公布了,才把那一天算進來:

- 在資料公布完之前執行,結果以前一個資料齊全的交易日為準。結果頁的「資料用到」會標明是哪一天。
- 想要拿到當天的資料,在晚上 9 點之後執行。

同一天重複執行會直接回傳已存的結果。服務以 UTC 的日期判斷是不是同一天,換算成台灣時間是早上 8 點換日。所以在資料公布完之前(例如晚上 7 點)執行過一次之後,當晚再執行仍然拿到以前一個交易日為準的那份結果。要補上當天的資料,等到隔天早上 8 點之後再執行;或者要求重新搜尋,但它會重做 Search。

## API

網頁能做的事都能經由 HTTP API 做,網頁本身也只呼叫這組 API。

- 後端在 http://localhost:8000,自動產生的互動式文件在 http://localhost:8000/docs。
- 網頁的位址也代理同一組 endpoint:http://localhost:3000/api/jobs 與 http://localhost:8000/api/jobs 是同一個 endpoint。健康檢查與 API 文件只在後端的位址。
- 欄位名稱與 [GLOSSARY.md](../GLOSSARY.md) 的用詞一致。
- API 只回傳預測與統計,不提供原始市場資料的下載,因為 FinMind 的條款不允許把原始資料轉給第三方。

| Endpoint | 用途 |
|------|------|
| `POST /api/jobs` | 發起執行 |
| `GET /api/jobs` | 列出排隊中與執行中的工作,依執行的順序排列 |
| `GET /api/jobs/{id}` | 查詢一個工作的狀態、階段、時間與失敗原因 |
| `GET /api/results` | 列出有結果的股票與 Horizon,以及各自最新的摘要 |
| `GET /api/results/{stock_id}/{horizon}` | 取得一支股票一個 Horizon 的 Backtest 與 Forecast |
| `GET /health` | 健康檢查 |

一次完整的流程:

```bash
# 發起執行。新的工作回 HTTP 202;今天已經有成功的工作時回 HTTP 200,並回傳那個工作
curl -s -X POST http://localhost:8000/api/jobs \
  -H 'Content-Type: application/json' \
  -d '{"stock_id": "2330", "horizon": 10}'
# {"id":1,"stock_id":"2330","horizon":10,"status":"queued","stage":null,"error":null,...}

# 每隔幾秒查一次,直到 status 變成 succeeded 或 failed
curl -s http://localhost:8000/api/jobs/1

# 取得結果
curl -s http://localhost:8000/api/results/2330/10
```

`POST /api/jobs` 的欄位:

| 欄位 | 說明 |
|------|------|
| `stock_id` | 股票代號,字串 |
| `horizon` | `5`、`10` 或 `20`,預設 `10`;其他值回 HTTP 422 並說明原因 |
| `re_search` | 預設 `false`;`true` 時不沿用已存的參數,重設起點並重新做 Search |

股票代號不存在時,發起本身會成功,工作在抓資料的階段失敗,`error` 說明查無這個代號。

工作的欄位:

| 欄位 | 說明 |
|------|------|
| `status` | `queued`(排隊中)、`running`(執行中)、`succeeded`(成功)或 `failed`(失敗) |
| `stage` | 執行中的階段:`fetch`(抓資料)、`search`(Search)或 `predict`(逐日預測)。工作結束後保留最後進入的階段 |
| `error` | 失敗原因;沒有失敗時是 `null` |
| `created_at`、`started_at`、`finished_at` | 發起、開始與結束的時間,UTC |

結果的欄位:

| 欄位 | 說明 |
|------|------|
| `data_date` | 資料用到的最後一個交易日 |
| `search_date` | 做 Search 找到這組參數的那一天 |
| `start` | 起點 |
| `backtest.accuracy` | 準確率;還沒有計分的日子時是 `null` |
| `backtest.scored_days` | 計分天數 |
| `backtest.direction_one_ratio` | 計分的日子裡實際 Direction 為 1 的比例;還沒有計分的日子時是 `null` |
| `backtest.days` | 計分的每一天的 `date`、預測的 `direction` 與實際的 `actual`,由舊到新 |
| `forecast` | 每一筆 Forecast 的 `date` 與 `direction`,由舊到新 |

還沒有結果的股票與 Horizon,`GET /api/results/{stock_id}/{horizon}` 回 HTTP 404。
